## Notes

### A. `autoFixable` is not an assessment — it is an artifact of which file the finding lives in

`Finding.auto_fixable` (`scripts/py/omnirank/report.py:52`) defaults to `False`, and **only `gates/seo.py` can ever set it**. Its local helper is the only one with the parameter:

```python
def _f(id_: str, gate: str, url: str, severity: str, observed: str,
       expected: str, fix: str, auto: bool = False) -> Finding:
```

The identically-named `_f()` helpers in `gates/jsonld.py`, `gates/aeo.py`, `gates/geo.py`, `gates/site.py`, `gates/perf.py`, and `gates/hygiene.py` have **no `auto` parameter at all**, and `audit.py` constructs `Finding(...)` directly without it. So 44 of 48 findings are `false` by construction, not by judgement — including `seo.schema.no-context` and `seo.canonical.chained`, which are as mechanical as the two canonical fixes that *are* marked true. Any future fix mode reading this field would skip both.

### B. Currently set `true` — 4 findings, all in `gates/seo.py`

| Finding | My tier | Agreement |
|---|---|---|
| `seo.canonical.missing` | MECHANICAL | ✅ agrees |
| `seo.canonical.relative` | MECHANICAL | ✅ agrees |
| `seo.h1.multiple` | ADVISORY | ❌ **disagrees** |
| `seo.description.long` | DRAFTED | ❌ **disagrees** |

### C. The two disagreements matter in opposite ways, and both are unsafe

**`seo.description.long` (`true`, should be DRAFTED).** The fix text is *"Clamp the description to 160 characters at a word boundary."* Clamping is trivially automatable — that is presumably why it is marked auto-fixable — but a clamped description is a **rewrite of public-facing copy**, and mid-sentence truncation ships a visibly unfinished snippet into every SERP result for that page. The mechanical operation is easy; the output is prose a human must approve. A fix mode acting on this field would edit marketing copy unattended.

**`seo.h1.multiple` (`true`, should be ADVISORY).** The fix text is *"Keep the first `<h1>`; demote the others to `<h2>`."* The rule is deterministic but **frequently wrong**: on any layout where a site-wide banner or logo renders an `h1` before the content region, "the first" is exactly the one that should be demoted. The gate has no signal for which `h1` is canonical — it only counts them (`gates/seo.py:19-27`). Applying this unattended inverts the document outline and changes rendered typography, and does so most reliably on the sites where the finding fires most.

### D. Two under-claims worth flipping to `true`

- **`seo.schema.no-context`** — the fix is a constant string (`"https://schema.org"`), additive and idempotent. The only obstacle is that the finding carries no pointer to the offending node (see note F).
- **`seo.canonical.chained`** — the finding text already names the terminal URL (`onward`) computed by the gate. The edit is a single `href` substitution with the value supplied.

Both are safer than `seo.description.long`, which is marked `true` today.

### E. Two findings in the table can never actually be emitted

`seo.crawl-hygiene.server-error` and `seo.crawl-hygiene.not-found` come only from `hygiene.check_removed()`, which `audit.py` never calls (confirmed against `CHANGELOG.md:38`, `docs/audit-guide.md:299`, and the v0.2.0 plan, which states it "remains unwired… needs a config field that does not exist yet"). The `crawl-hygiene` gate name is also **absent from `audit.failOn`'s enum** in `schemas/omnirank.config.schema.json`, so it cannot even be selected. They are tiered above for completeness; a fix mode would never see them.

### F. Structural gaps that block a fix mode regardless of tier

1. **No source-location field.** Every finding identifies a *URL*, never a file, line, or template. Every tier above MECHANICAL-on-static-HTML first requires a URL→source mapping the report does not provide. `config.stack.srcDir` / `builtHtml` exist but are never consumed by the audit path.
2. **No node pointers in JSON-LD findings.** `seo.schema.no-type` and `seo.schema.no-context` say *what* is wrong but not *where* — `extract_blocks()` flattens `@graph` and discards the origin script index and path (`gates/jsonld.py:27-48`). A fixer must re-parse and re-derive the location, and can guess wrong when several nodes share a type.
3. **Fix target ≠ `finding.url` for `seo.hreflang.not-reciprocal`.** The edit belongs on the page at the `href` inside the finding *text*, not on `finding.url`. This is parseable only from prose. Any fixer keyed on `finding.url` silently edits the wrong page and the finding persists.
4. **Dropped observations.** `seo.sitemap-health.redirect` records the status but discards the `Location` header that *is* the fix. `seo.image.no-dims` truncates to 3 `src` values (`gates/seo.py:107`) while reporting a count that may be far larger — a fixer cannot enumerate its own work list.
5. **Findings with two opposite fixes are not distinguishable from single-fix findings.** `seo.noindex.in-sitemap`, `seo.sitemap-health.dead-url`, `seo.page.unreachable`, `seo.schema-fabrication.*`, and `seo.duplicate-title.shared` all encode an either/or in the `fix` *prose* with nothing structured marking it. This is the single strongest argument for replacing the boolean with the five-value tier: a boolean cannot express "there are two correct answers and only a human can pick."

### G. Documentation drift on this field

`docs/wiki/Report-Schema.md:44` describes `autoFixable` as *"Present and `true` only on findings OmniRank could, in principle, patch itself… absence means false."* But `Finding.to_dict()` (`report.py:54-65`) **always** emits the key, so the documented absence case never occurs, and `false` in a report means "the gate module has no `auto` parameter," not "OmniRank assessed this as unfixable." The schema correctly marks the field optional; the emitter does not exercise that.

### H. Recommendation if a fix mode is built

Replace `autoFixable: boolean` with `fixTier: "mechanical" | "templated" | "drafted" | "advisory" | "infrastructure"` in `schemas/report.schema.json`, add the parameter to the `_f()` helper in **every** gate module (not just `seo.py`), and gate unattended application to `mechanical` only — which after the corrections above is 4 findings: `seo.canonical.missing`, `seo.canonical.relative`, `seo.schema.no-context`, `seo.canonical.chained`. Keeping the boolean and honouring it as-written would auto-apply two unsafe fixes (`seo.h1.multiple`, `seo.description.long`) and skip two safe ones.
